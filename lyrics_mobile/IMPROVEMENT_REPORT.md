# 가사 읽기·검색·AI 요청 개선 보고서

## 범위와 결론

2026-10-30 작업. 기존 Android 앱을 유지하면서 읽기 화면, 사용자 동작 피드백, 검색과 원문 선택, AI 요청 및 진단을 수정했다. 카라오케는 추가하지 않았고 ACRCloud는 비활성 준비 상태를 유지했다.

화면 문제는 앱 코드에서 수정하고 API 36 에뮬레이터로 확인했다. 개인 API 키를 사용하거나 유료 GPT/Gemini 생성을 실행하지는 않았다. 따라서 사용자가 보고한 약 50% 실패율의 원인이 모두 밝혀졌다거나 실제 실패율·번역 시간이 개선됐다는 수치는 주장하지 않는다.

## 1. 화면과 사용자 동작

- 가사 상세창은 고정 제목/탭/상태 영역, 하나의 가사 스크롤 영역, 하단 읽기 설정/곡 메뉴로 재구성했다. 중첩 세로 스크롤을 없애고 본문에 남은 높이를 배정했다.
- 기본 '함께 보기'에서 원본·번역·발음을 같은 줄 단위로 묶는다. 원본/번역/발음 단독 탭도 유지한다. 빈 연과 원문의 줄 위치를 보존한다.
- 읽기 설정에서 표시 항목, 글꼴 계열, 크기, 간격, 움직임을 선택한다. 기본은 원본+번역이며 발음은 선택 사항이다. 함께 보기에서 선택한 생성 항목은 자동으로 요청되므로 API 사용량이 발생할 수 있다.
- 진행 중에는 실제 회전 ProgressBar와 처리 중인 제공자·기능·구간을 보여준다. 백분율을 임의로 만들어 보여주지 않는다. 취소는 진행 중 HTTP 호출까지 전달한다.
- 버튼 눌림은 약 90ms 축소/140ms 복귀와 리플·햅틱으로 피드백한다. 화면·가사창·탭 내용은 약 200ms 전환, 검색 결과는 처음 6개까지만 짧게 순차 등장한다. 진행 상태가 바뀔 때마다 가사 본문 전체를 새로 만들거나 스크롤을 처음으로 되돌리지 않는다.
- 움직임은 읽기 설정에서 끌 수 있고 시스템 애니메이션 배율이 0이면 장식 전환을 하지 않는다. 로딩 표시 자체는 남아 작업 상태를 알 수 있다.
- 파란색 패널 중심 구성을 줄이고 중립적인 배경/본문 대비, 여백, 선택 상태로 위계를 정리했다. ivLyrics의 웹 UI를 그대로 이식한 것이 아니라 Android 입력·스크롤 구조에 맞게 재구성했다.

## 2. GPT-5 mini 지연과 요청 실패

### 확인한 구현상의 위험

- 전체 가사를 한 요청으로 생성하고 줄 수를 엄격하게 검사하던 구조에서는 모델이 빈 줄을 합치거나 줄을 나누기만 해도 결과를 버릴 수 있었다. 이는 네트워크 연결 실패와 다른 출력 형식 실패다.
- GPT-5 mini 요청에 reasoning 설정이 없었다. 공식 예제는 해당 초기 GPT-5 계열의 기본 reasoning effort가 medium이며 minimal이 지연을 줄이는 선택임을 설명한다. 실제 계정 지연의 단독 원인이라고 단정할 수는 없다.
- 짧은 연결 테스트 성공은 긴 가사의 생성 성공을 보장하지 않는다. 출력 길이, 처리 시간, 속도/사용 한도, 콘텐츠 거절, 제공자 장애가 별도로 영향을 준다.
- 사용자 당시 요청의 HTTP 코드·응답·시간 기록이 없어 '두 번 중 한 번 실패'의 정확한 원인은 소급 확정할 수 없다.

### 적용한 변경

- 원문 줄 ID를 붙여 최대 24개 비어 있지 않은 줄씩 요청한다. 앞뒤 최대 3줄 문맥을 함께 주고 의미·화자·정서·비유를 보존하도록 지시한다. 발음 작업은 번역과 구분한다.
- 응답 JSON의 ID 중복/누락/범위와 본문을 검증하고 원래 순서 및 빈 줄을 복원한다. 출력 형식 오류는 LINE_MISMATCH로 구분한다. 프롬프트 형식 지시와 앱 검증이며 서버 측 JSON Schema 보장 기능을 적용했다는 뜻은 아니다.
- 검증된 구간은 별도 캐시한다. 뒤 구간 실패 후 사용자가 다시 시도하면 동일 요청의 성공 구간을 재사용할 수 있다. 전체가 검증되기 전에는 완성된 번역으로 저장하지 않는다.
- 정확히 초기 gpt-5/gpt-5-mini/gpt-5-nano 및 해당 날짜 버전에서만 reasoning.effort=minimal을 보낸다. 다른 모델에 무조건 적용하지 않는다.
- 번역/발음 요청을 직렬 큐로 처리하고 중복 요청을 막는다. GPT 우선 및 조건부 Gemini 1회 대체 규칙은 유지한다. 취소·명시적 콘텐츠 거절은 우회 대체하지 않는다.
- 설정에 마지막 AI 요청 진단을 추가했다. 제공자·모델·안전한 오류 코드·소요 시간만 기록하고 키, 원문, 번역 전문이나 원시 오류 응답은 기록하지 않는다.

### 남는 한계

분할 요청은 한 번의 출력 부담과 재시도 낭비를 줄이지만 요청 횟수·문맥 토큰은 늘어난다. 전체 시간이 항상 줄거나 비용이 반드시 낮아지는 것은 아니다. 연결/읽기/전체 호출 제한은 각각 20/90/120초이고 서버·계정·네트워크 문제 자체를 없애지는 못한다. 타임아웃 뒤 서버 과금 여부는 확정할 수 없으며 Gemini 대체도 추가 사용량을 소모할 수 있다. 진단은 마지막 요청 기준이며 장기 통계가 아니다.

공식 근거: [GPT-5 파라미터 예제](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5_new_params_and_tools), [GPT-5 mini 모델 문서](https://developers.openai.com/api/docs/models/gpt-5-mini).

## 3. 곡을 찾는 방식과 Vaundy 누락 원인

현재 재생 버튼은 플레이어가 공개 MediaSession으로 제공한 제목·가수를 읽는다. 주변 소리를 인식한 결과가 아니며 메타데이터를 주지 않는 플레이어는 수동 검색이 필요하다.

기존에는 KR 25건 조회 후 결과가 없을 때만 US를 조회했다. 다른 가수의 동명곡이 있으면 멈추고 JP는 확인하지 않았다. 라이브 제목 정리 분기에서 가수까지 빠지는 문제도 있었다.

지금은 명시적인 Official Video/Live at/Topic/THE FIRST TAKE 장식과 채널명을 정리하되 정상 제목의 Live 같은 단어는 보존한다. JP/KR/US 카탈로그 결과를 병합하고 곡 ID·가수·제목·길이로 중복을 줄인다. 가수 일치와 제목 일치 후보를 우선하고 사용자가 결과를 선택한다.

`tomoshibi`는 세 국가 검색만으로도 Vaundy가 나오지 않는 공개 응답을 확인했다. 일본어 `灯火`에서는 같은 가수의 실제 카탈로그 곡이 나왔다. 따라서 '곡 자체가 없다'가 아니라 로마자 검색 색인의 한계였다.

MusicBrainz의 공개 작품 별칭에서 정확히 일치하는 로마자 표기를 찾아 일본어 등의 원제 후보로 검색을 확장한다. 작품 별칭은 철자 후보일 뿐 같은 가수/녹음임을 증명하지 않는다. 특정 Vaundy 곡을 하드코딩하지 않고 다시 실제 카탈로그를 조회한다.

### 실제 앱 검색 코드로 확인한 표본

| 입력 | 결과 | 소요 시간 |
| --- | --- | --- |
| tomoshibi | 灯火 / Vaundy, catalog ID 1706831934 포함 | 약 5.97초 |
| Vaundy「しわあわせ」(Live at Budokan) [Official Video], 가수 Vaundy - Topic | しわあわせ / Vaundy, ID 1706829387 포함 | 약 1.95초 |

개인 키 없는 실제 공개 서비스 호출 1회씩의 관찰값이며 성능 보장이나 평균값이 아니다. 넓은 검색 결과에는 관련도가 낮은 곡도 포함되므로 '원곡 인식 완료'로 표시하지 않는다. 별칭 DB에 없는 음역이나 잘못 적은 제목을 모두 복원할 수는 없다. 일부 국가/별칭 조회 실패는 결과가 누락될 수 있다는 안내를 남긴다.

별칭 조회를 포함한 검색 예산은 약 24초, 국가별 호출 최대 6초, 별칭 조회 최대 5초로 제한한다. MusicBrainz는 프로세스 내 요청 간격을 제한한다. 배포 전 실제 연락처를 포함한 User-Agent, 서비스별 호출량 제어, 상업적 이용 조건 검토가 필요하다. [MusicBrainz API](https://musicbrainz.org/doc/MusicBrainz_API), [호출 제한](https://musicbrainz.org/doc/MusicBrainz_API/Rate_Limiting).

## 4. 일본 노래의 원본이 라틴 문자였던 이유

기존 앱은 LRCLIB의 plainLyrics를 원본으로 그대로 표시했다. 이 DB에는 로마자 표기 등록본도 있을 수 있다. 사용자가 봤던 정확한 곡 ID/본문은 확보하지 못했으므로 해당 사례가 영어 번역인지 로마자인지는 단정하지 않는다.

같은 등록본의 syncedLyrics에 일본어/한국어 문자가 있으면 타임스탬프를 제거해 본문으로 사용할 수 있게 했다. 대체 등록본은 제목·가수·알려진 길이 ±2초가 맞는 경우만 검토하며, 메타데이터에 원문 문자 근거가 있을 때 원제 표기를 우선한다. 없는 원문을 AI로 역번역해 만들지 않는다.

원본 탭과 출처에는 문자 정보를 표시한다. 라틴 문자만으로 영어와 일본어 로마자를 확정할 수 없어 '라틴 문자 · 언어 미확인/로마자 가능'으로 안내한다. 한자만으로도 일본어를 확정하지 않는다. 등록본이 없거나 메타데이터가 다르면 원문 확보가 여전히 불가능할 수 있다.

LRCLIB의 灯火/Vaundy/179초 조회에서 일본어 등록본을 확인했다. 별도 Tomoshibi 조회의 503 ServerOverloaded는 '가사 없음'이 아니라 서비스 과부하였다. 상세 조사: [SEARCH_FINDINGS.md](SEARCH_FINDINGS.md).

## 5. ivLyrics 참조 범위

[ivLyrics 저장소](https://github.com/ivLis-Studio/ivLyrics)의 AIRequest.js, Addon_AI_ChatGPT.js, TranslationModeHelper.js를 확인했다. 요청 취소·시간 제한, 모델별 옵션 분기, 번역과 발음 처리 분리 및 언어 정보 활용을 Android 구조에 반영했다. Spotify/Spicetify의 웹 UI·재생 환경과 Android MediaSession은 다르므로 동일한 재생 제어/싱크 기능을 제공한다고 주장하지 않는다.

번역의 문학적 풍부함은 키 자체보다 프롬프트·모델·앞뒤 문맥과 번역 목적에 영향을 받는다. 이번에는 단순 단어 치환 대신 화자·정서·비유를 유지하도록 요청하지만 과장하거나 없는 의미를 더하도록 지시하지 않는다. 분할 구간 경계의 표현 일관성은 실제 노래별 품질 검수가 추가로 필요하다.

## 6. 저장·검증·주의 사항

- 검색 regional/current-v2, 원문 native-v2, AI v4-indexed 키로 예전의 잘못된 검색/로마자/줄 정렬 결과를 그대로 재사용하지 않게 했다. 이 변경 후 최초 요청은 기존 데이터가 있어도 다시 조회/생성될 수 있고 AI 비용이 발생할 수 있다.
- 성공한 동일 구간은 캐시한다. 파일 누락/손상은 캐시 미스로 다루고 필요한 데이터를 재요청한다. 무제한 무과금 재사용 보장은 아니며 만료/용량 정리 정책은 유지한다.
- JDK 20, compileSdk/targetSdk 36으로 빌드했다. 단위 테스트 49개, API 36 에뮬레이터 계측 테스트 13개 통과. Lint 오류 0개, 경고 24개. 경고가 없는 상태는 아니다.
- 80줄의 합성 일본어/한국어/발음 함께 보기에서 마지막 줄 도달, 스크롤 위치 재생성 복원, 탭 정렬, 작업 표시/취소를 검증했다. 실제 유료 생성·전체 단말/최대 글꼴 배율 조합은 검증 범위가 아니다.
- 실제 사용자 휴대폰에는 설치·초기화하지 않았다. 개인 키를 로그나 보고서에 포함하지 않았다. 과거 대화에 공개된 키는 재사용하지 않았으며 해당 키는 제공자 콘솔에서 폐기·재발급하는 것이 안전하다.
- 가사 데이터 저장/표시/배포 권리와 외부 서비스 이용 조건은 별도 검토가 필요하다.

## 2026-11-03 LRCLIB 503 조사 결론

### 확인된 사실
- 곡 검색은 카탈로그, 원문 조회는 LRCLIB를 사용하므로 곡 검색 성공이 가사 서버 정상 상태를 보장하지 않는다.
- 503은 서버가 요청을 처리할 수 없다고 응답한 상태다. 네트워크 무응답/404 가사 없음/AI 결제 오류와 다르다.
- 공식 서버 아키텍처에는 동시 처리 예산 소진 시 503 + Retry-After: 1을 반환한다고 명시돼 있다. https://github.com/tranxuanthang/lrclib/blob/main/ARCHITECTURE.md
- 공개 API 진단은 get 200(5.355초), search 200(2.112초). 개인 키나 가사 내용은 로그에 남기지 않았다. 사용자 당시의 원시 응답이 없어 과부하/점검/프록시 문제 중 어느 것이었는지는 확정하지 않는다.

### 앱에서 개선한 것
- 503/502/504/429/NOT_FOUND를 구분하고 원인 가능성 및 해결 행동을 안내한다.
- 가사 서비스 오류 팝업에 재시도/직접 입력, 상세 화면에도 동일 경로를 유지한다.
- NOT_FOUND에서만 기존 AI 동의 흐름으로 이동. AI가 서버 장애를 해결한다고 안내하지 않는다. 현재 AI 복구는 메타데이터 보정 후 동일 LRCLIB 재조회이며 별도 웹 가사 제공처가 아니다.
- 원문 파일은 월별 만료 없이 재사용한다. 20MiB 제한/사용자 초기화/파일 손상의 경우는 예외이며 화면에 명시한다.
- 설정에 최근 LRCLIB 응답 코드/시간을 기록한다. 서버 오류 페이지, 가사, 곡명, API 키는 기록하지 않는다.
- 공식 서버의 503을 앱 수정으로 없앴다고 주장하지 않는다. 서버 정상화 시간도 보장하지 않는다.

### 디자인
- 기본 B안: 차콜과 라임. 설정에서 오렌지 외곽/그린 내부 테마 선택, 재실행 유지.
- 큰 재생 곡 버튼, 실제 카탈로그 아트와 목록 전체 터치, 원문 언어가 표시되는 가사 탭 유지.
- 화면 캡처는 API 36 에뮬레이터이며 합성 테스트 기록이 포함될 수 있다. 실제 유료 AI 호출/사용자 휴대폰 테스트는 수행하지 않았다.

최종 검증: 단위 테스트 66개 / API 36 계측 18개 통과, APK 빌드 성공, Lint 0 errors / 25 warnings. 503 mock, 장기 원문 캐시, 테마 재생성, 직접 입력 경로 및 기존 동의·스크롤 회귀 포함. 실제 유료 API 호출은 검증하지 않음.
